# Food capture sources and limits

Reviewed 2026-11-06. No live OpenAI request was made during development. API behavior is checked with mocked responses.

## Offline reference catalog

Nineteen FDA entries are **raw edible fruits** from the FDA's [Raw Fruits Poster, accessible text version](https://www.fda.gov/food/nutrition-food-labeling-and-critical-foods/raw-fruits-poster-text-version-accessible-version). These are rounded labeling values, not a comprehensive analytical food composition database. The exact source serving mass is retained as `source.referenceGrams`. Each stored per-100g amount is the published serving amount multiplied by `100 / referenceGrams`; consumed amounts are subsequently multiplied by edible grams / 100. This arithmetic does not improve the precision of the source.

Only energy, total fat, sodium, potassium, carbohydrate, dietary fiber and protein are transcribed. Values published as zero stay zero **with the rounding caveat**; unlisted nutrients are omitted and remain unknown. Vitamin/mineral %DV columns are deliberately not reverse-converted to nutrient masses. These historical label %DV values must not be used as current personal nutrient targets. Other foods outside this small catalog remain unresolved rather than receiving invented matches.

Text parsing accepts explicit grams and an exact catalog name or alias, separated by commas, semicolons or newlines, for example `126g banana, 242g apple`. It retains each unresolved segment and its reason. The user must review a draft before any save. Cooked and raw foods must not be interchanged.

## USDA varied reference foods

Eleven exact SR Legacy records were retrieved from the official [USDA FoodData Central API](https://fdc.nal.usda.gov/api-guide/) with its documented public exploration credential DEMO_KEY. These cover dry oats, cooked enriched white rice, roasted chicken breast, hard-boiled egg, vitamin-D-fortified whole milk, boiled unsalted lentils, raw spinach, olive oil, cooked farmed Atlantic salmon, almonds and raw banana. The USDA banana replaces the rounded FDA banana reference. `100g oats, 150g banana` produces two weighed drafts. Each food retains its exact FDC ID, source description, preparation and access date.

`docs/usda-source-snapshot.json` preserves the relevant original nutrient IDs, names, units and amounts per 100g, together with hashes of the two retrieved API response bodies. The original full bodies were not committed. The committed snapshot is sufficient to audit every mapped nutrient. Tests compare every snapshot value to the embedded runtime catalog and check portion scaling. No private API key or runtime USDA dependency is needed. USDA states these data are public domain, CC0 1.0; attribution: U.S. Department of Agriculture, Agricultural Research Service, FoodData Central.

Mappings use only exact nutrient IDs and units: vitamin A uses ID 1106 (RAE in micrograms), folate uses ID 1190 (DFE in micrograms), vitamin E uses ID 1109 (alpha-tocopherol in mg), vitamin D uses ID 1114 (D2+D3 in micrograms), and vitamin K uses ID 1185 (phylloquinone in micrograms). IU, total folate, folic acid and other tocopherols are not substituted. Missing nutrient records stay missing. Reference zeros may reflect source assumptions or composition conventions; this is generic reference composition, not a measurement of the user’s food.

## Optional barcode lookup

This uses a read-only GET to the fixed official Open Food Facts v2 product endpoint. See the [official introduction](https://openfoodfacts.github.io/openfoodfacts-server/api/) and [official v2 API specification](https://github.com/openfoodfacts/openfoodfacts-server/blob/main/docs/api/ref/api.yaml). Each result links to the specific product. Attribution: **Open Food Facts contributors**, database licensed under [ODbL 1.0](https://opendatacommons.org/licenses/odbl/1-0/). Reusers must check attribution and share-alike obligations for their resulting database; cached or exported product records retain their source/license metadata.

Community supplied values can be incomplete, out of date or incorrect. Verify the product and package label. Only explicit finite nonnegative numeric `_100g` values are accepted. Macro amounts use grams; sodium and the supported mineral fields are normalized from OFF's grams to Nutrak's milligrams. Energy accepts `energy-kcal_100g` only; kJ is not mislabeled as kcal. Missing and invalid amounts are omitted, not replaced with zero. Serving values are never silently substituted for per-100g data. Do not use this mass-based lookup to log a liquid by millilitres without a known density. There are no writes, automatic retries, or background lookups. Requests support AbortSignal and a bounded timeout. The application identifies itself; browsers may control or strip User-Agent headers.

## Optional personal OpenAI photo draft

The implementation follows OpenAI's official [image input guide](https://developers.openai.com/api/docs/guides/images-vision?api-mode=responses), [structured outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs), and [Responses create reference](https://developers.openai.com/api/reference/resources/responses/methods/create). Default: `gpt-4.1-mini`, a documented image-capable smaller model. Model name can be changed explicitly; syntactic validation does not guarantee availability or capability. Images are sent as base64 `input_image` with low detail; outputs use strict JSON schema plus independent application validation.

**This direct browser BYOK feature is intended for personal use.** A key entered in a browser is exposed to that browser runtime and any code/extensions with access. It is not an appropriate way to ship a shared production API secret. Use a restricted personal key, protect the device, and revoke it when needed. Production multiuser hosting should place credentials in a backend with authentication, spending controls and a privacy policy. OpenAI advises keeping keys out of browser client code: [API key safety](https://help.openai.com/en/articles/5112595-best-practices-for-api-key-safety).

The key is passed to one `analyze()` call and is not stored, logged, exported or placed in a URL. The image and key are sent only to the fixed HTTPS OpenAI endpoint after the user's explicit action. Each call can incur API charges. No retries run automatically. `store:false` is set, but that is not a promise of zero provider retention; OpenAI's [data controls](https://developers.openai.com/api/docs/guides/your-data) describe separate abuse monitoring and retention policies. Avoid photos containing people, private documents or unnecessary metadata.

Supported inputs are JPEG, PNG and WebP base64 data URLs, with a 4 MiB encoded image payload cap. The UI can resize before sending. Portion estimates and visible food identities can be wrong; hidden oils and ingredients cannot reliably be recovered. The model provides only total portion energy and macros, not micronutrients or confidence percentages. Unknown amounts remain null. Refusals, incomplete output, malformed JSON, excessive counts, impossible types, negative amounts, excessive ranges, cancellation and HTTP errors fail visibly. The response is always an editable draft with source metadata. Nothing is automatically logged.
